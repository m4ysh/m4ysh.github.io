Writing Eval Harnesses That Survive a Refactor

The eval harness is the part of the system that decides whether the things you ship are actually getting better or whether you are just convincing yourself they are. This post is about the three layers every harness needs, the manifest that makes a run reproducible, the anchor runs that catch silent regressions, and the discipline that makes the rest of the numbers worth looking at.

// 01   THE NUMBER THAT WASN'T

The model changed on a Tuesday. The benchmark ran on a Wednesday. The number went up. The number going up was not the surprise. The surprise was that nobody could tell whether the number going up meant the model got better or the benchmark got easier. The prompt had been edited the week before. Two tasks had been "slightly simplified" by an engineer who had since left the team. A scorer had been "fixed" six weeks earlier and never re-validated. By Wednesday, the harness was measuring a different thing than it had been measuring on Monday. We had a number. We did not have a result.

The interesting thing about this kind of failure is that it is invisible in the moment. The benchmark runs. The number comes out. The number is higher than last week's number. The model shipped an update. The update looks better. Everyone is happy. The regression is six months away, when someone asks "wait, when did the benchmark start measuring that?" and the answer is "we don't know, it's been months."

The pattern is not unique to our team. It is the default failure mode of any eval suite that has been alive for more than a year. The suite accretes changes. The changes are small. The changes are reasonable in isolation. The changes compose into something that is no longer the thing you set out to measure. The composition is invisible because the suite does not have a manifest. The suite has a number. The number is a story you are telling yourself.

The fix is a harness with a manifest, with frozen layers, and with anchor runs that catch silent drift. The fix is not glamorous. The fix is mostly bookkeeping. The fix is the part of the system that does not ship to users. The fix is the part that decides whether the things you ship are actually getting better.

// 02   THE THREE LAYERS

A good eval harness has three layers, and they should be versioned independently. The first is the task suite: the inputs (questions, contexts, ground-truth outputs) and the scoring rubric. The second is the runner: the plumbing that invokes the system under test, collects outputs, and handles retries and timeouts. The third is the scorer: the grading logic that turns outputs into numbers.

The three layers have different change cadences. The task suite changes when you add a task, remove a task, or fix a task that was wrong. The runner changes when you fix a bug in the harness, switch a retry policy, or update a dependency. The scorer changes when you change what "correct" means. The changes are not independent in intent, but they should be independent in versioning. A change to the scorer should not touch a line of the task suite. A change to the runner should not touch a line of the scorer.

The implementation is three repos. We have a tasks repo (the task suite), a runner repo (the plumbing), and a scorers repo (the grading). Each has its own CI. Each has its own test suite. Each has its own versioning. An experiment pins a commit from each repo, plus the model id, plus the prompt template, plus the runner environment. The combination is the manifest. The manifest is the reproducibility.

The alternative is a single repo with a /tasks, /runner, /scorers directory structure. The alternative is simpler in tooling, but the layers are coupled by the repo. A change to the runner requires a PR that touches the runner. A change to the scorer requires a PR that touches the scorer. The coupling is fine if the team is small. The coupling becomes friction when the team grows.

// 03   FROZEN MANIFESTS

Every experiment gets a frozen manifest. The manifest pins the exact commit of the task suite, the exact commit of the scorer, the exact model id and provider version, the exact prompt template, and a hash of the runner's environment. The manifest is stored alongside the result. Six months later, when someone asks "what was the model doing at that 41.2% number," you can reproduce the exact run, including the bug that you only noticed afterwards. 

run_manifest = {
    "task_suite": pin("git+ssh://eval/tasks.git@a1b2c3"),
    "scorer":     pin("git+ssh://eval/scorers.git@4d5e6f"),
    "model":      {"provider": "anthropic", "id": "claude-opus-4-7", "rev": "2025-11-20"},
    "prompt":     sha256_file("prompts/main.j2"),
    "env":        sha256_file("requirements.lock"),
}
write_manifest(run_manifest, path=f"runs/{run_id}.json")

The manifest is the part of the system that should never be edited after the run. The result is a function of the manifest. The manifest is the input to the function. The function is the run. The result is the output. The output is meaningless without the input. The manifest is the input.

The manifest also makes audits possible. A regulator asks "what was your model doing on March 14, 2026?" The answer is a manifest. The manifest pins the task suite, the scorer, the model, the prompt, the environment. The answer is reproducible. The answer is auditable. The answer is the difference between a model you can deploy in a regulated context and a model you cannot.

The implementation is small. A write_manifest function that takes a dict and writes it to a file. A read_manifest function that reads it back. A convention that every run directory contains a manifest.json. A CI check that fails the build if a result is written without a manifest. The cost is bookkeeping. The benefit is reproducibility.

// 04   CALIBRATION RUNS

On a fixed cadence (weekly, in our case) we run the full harness against a small set of anchor models that we never ship with. The anchors are cheap, slow-changing, and well understood. GPT-3.5-turbo is one. Claude Instant is another. Llama-3-8B is a third. The anchor suite is the same task suite with the same scorer. The model is the only thing that changes.

If an anchor's number moves by more than a configured delta (we use 0.5 absolute percentage points), we investigate before we trust any of the other numbers. The investigation is almost always one of three things: a silent scorer regression, a prompt-template change, or a provider-side update that nobody told us about. We caught a Claude prompt-cache change this way in November 2025. Without the anchor, we would have shipped a "regression" that wasn't.

The anchors are not perfect. They are subject to the same provider-side changes as the models we ship with. The difference is that we have years of anchor data. We know what the anchor's number should be. We know what the variance should be. A 0.5-point move is a signal. A 0.1-point move is noise. A 2-point move is an investigation. The thresholds are calibrated to the anchor's history. The thresholds are not transferable to other models. Each anchor has its own threshold.

The cost is real. Running an anchor suite weekly is a small but non-zero line item. The benefit is that the rest of the numbers are worth looking at. That is the trade, and most teams do not make it. Most teams run the eval suite when they ship a model, see a number, and ship. The number is a story. The anchor is the only way to know whether the story is true.

// 05   WHEN THE SCORER IS WRONG

You will discover, with non-trivial frequency, that the scorer is wrong. A task that should have been marked correct is marked wrong, or vice versa. The failure modes are predictable. The scorer compares a normalized string and a regex matches "nope" to "nope." with the difference being a trailing period. The scorer compares a numeric answer and rounds 0.499 to 0 when the answer is 0.5. The scorer parses a JSON output and fails on a trailing comma. The scorer is a program. The program has bugs.

The right move is almost never to fix the scorer and keep going. The right move is:

  1. Mark the affected run ids as scorer_bug in the manifest.
  2. Re-run them with the corrected scorer and a frozen task suite.
  3. Compare the new number to the old. If the delta is small, you are done. If the delta is large, write up what happened.

The writeup matters. Future-you will thank present-you. The next person who joins the team will not have to reverse-engineer why a number is what it is. The writeup is the institutional memory of the eval suite. The institutional memory is the part that does not survive a team transition. The writeup is how you make it survive.

The discipline of "mark, re-run, compare" is what separates a harness from a number generator. The harness is a system that can be inspected, audited, and reproduced. The number generator is a script that produces a number. The number is the same in both cases. The system is different. The system is what matters.

// 06   CONTAMINATION

The single hardest problem in eval is contamination. A model is trained on a corpus. The eval suite is a dataset. If the dataset is in the corpus, the model has seen the answers. The model is not "solving" the task. The model is recalling the answer. The eval is not measuring capability. The eval is measuring recall. The two are not the same.

The standard mitigations are well-known. Held-out test sets. Dynamic benchmarks where the questions are generated at eval time. Private benchmarks that are not released publicly. Multiple-choice questions with randomized answer orders. None of the mitigations are perfect. All of the mitigations are necessary.

GSM8K (Cobbe et al., 2021) was a good benchmark for about six months. By 2023, every frontier model was scoring above 90%. The benchmark was either trivial or contaminated. Probably both. MATH (Hendrycks et al., 2021) went the same way. HumanEval (Chen et al., 2021) is now saturated for production-sized models. The benchmarks that survive contamination are the ones that get refreshed. The benchmarks that do not get refreshed die.

Our strategy is two-pronged. The first prong is to maintain a private eval suite that is never released. The private suite has roughly 2,000 tasks, refreshed quarterly. The refresh is expensive (a few engineer-weeks per cycle) but the suite is the most trusted signal we have. The second prong is to use public benchmarks with a clear eye on their saturation. A benchmark that every model scores 95% on is not measuring what it used to measure. We deprecate saturated benchmarks from our internal leaderboard. The deprecation is documented. The deprecation is the answer to "why did you stop reporting this number?"

The deeper problem is that contamination is asymmetric. The model trains on the corpus. The eval suite is part of the corpus, by accident or by design. The model does not know which parts of its training data are "the test." The eval suite does not know which parts of the model's training data are "the answers." The two are coupled in a way that neither side can fully characterize. The coupling is the limit of what any benchmark can tell you about a model's capability.

// 07   CAPABILITY VS ALIGNMENT EVALS

Capability evals and alignment evals are different systems. They measure different things. They have different failure modes. They require different harnesses.

Capability evals ask "can the model do X." The answer is a number. The number is reproducible. The number is comparable across models. The number is what gets reported in leaderboards. The number is what gets used in marketing. The number is, in the limit, what determines whether a model ships.

Alignment evals ask "does the model do X when it shouldn't." The answer is a rate. The rate is the number of times the model did X out of the number of times it was asked. The rate is harder to reproduce. The rate depends on the prompt distribution. The prompt distribution is a modeling choice. The modeling choice is a research decision. The research decision is load-bearing.

A capability eval can be graded by a Python function (see LOG 001 on verifiable rewards). An alignment eval cannot. An alignment eval requires a judge, and the judge is a model (or a human, or a model reviewed by a human), and the judge has biases (see LOG 001 on position and length bias). The biases are measurable. The biases are not eliminable. The biases are part of the number.

The harness for an alignment eval must therefore include the judge's bias report. The report is part of the manifest. The report is the audit trail. The audit trail is the difference between a claim of "our model is 95% safe" and a defensible claim of "our model is 95% safe on the red-team distribution, judged by Claude-Sonnet-4.5, with a 3% position bias and a 2% length bias, corrected for both." The first claim is a story. The second claim is a result. The harness is the difference.

// 08   POST-MORTEM

A few things I want to flag from our own work. The first is that the harness is the part of the system that needs the most care, and the part that gets the least, because it is the part that does not ship to users. The "doesn't ship" property is the trap. The harness is the part that decides whether the things that ship are actually getting better. The asymmetry between visibility and importance is the whole problem with eval, and the harness is the only answer I have found.

The second is that contamination is a moving target. A benchmark that is fresh today is contaminated in six months. The refresh cadence is the only sustainable defense. The refresh is expensive. The refresh is necessary. The alternative is a leaderboard full of 99% numbers that nobody trusts.

The third is that the anchor runs are the most under-rated part of the system. The anchors are the part that catches the silent regressions. The silent regressions are the part that destroys trust in the eval suite. The trust is the part that determines whether anyone believes the numbers. The anchors are the foundation. The foundation is unglamorous. The foundation is necessary.

The eval harness, the manifest format, the anchor suite, and the contamination writeup are documented in the eval-systems repo. The full source, the calibration schedules, and the private benchmark refresh process are at huggingface.co/spaces/nebiuz/eval-systems. The harness builds on the lm-evaluation-harness design, the HELM methodology, and the OpenAI Evals framework, with the contamination discipline of LiveBench and the manifest pattern of the EleutherAI evaluation harness.

// ACKNOWLEDGMENTS

The harness design draws on a long lineage of eval systems. The task / runner / scorer separation follows the EleutherAI lm-evaluation-harness design. The holistic multi-metric framing follows the HELM methodology. The contamination discipline follows the LiveBench approach. The manifest pattern follows the broader ML reproducibility literature. The "number plus the conditions that produced it" framing is a synthesis of all of the above. The capability / alignment split follows the standard taxonomy in the alignment literature. The anchor-suite discipline is the one piece I have not seen described in print before, though it may be in use elsewhere. If someone has written it up, I'd like to know.
