State Leakage in Agent Environments

Reproducible agent evaluation is a hermeticity problem. The model, the prompt, and the dataset get the attention because they are the visible inputs. The environment is supposed to be invisible. When it stops being invisible, the numbers drift, the regression searches fail, and the bug ends up being a tokenizer. This post is about the four families of leakage I have hit, the one technique that has caught more of them than anything else, and what they cost in practice.

// 01   THE DRIFT

The first time I noticed state leakage, I didn't notice it. A baseline I had been running for two weeks on an interpretability task started coming in lower. Not by much. The first run on Monday was 41.2%. Wednesday it was 39.8%. Friday, 38.4%. The numbers walked down a slope, slowly enough that the rolling averages hid it for a week. I assumed a model regression. I assumed a prompt regression. I checked the dataset. The dataset was the same. The prompt was the same. The model was the same checkpoint. The evaluation harness was the same. The container image was, in theory, the same.

The container image was not the same. The tokenizer cache that the env kept at module scope was using, on the second run, a tokenizer object that had been initialized with a different vocabulary mapping than the one the test fixtures expected. The vocab mapping had not changed. What had changed was which key in the cache had been warmed first. The first episode of the first run warmed a key for vocab A. The first episode of the second run warmed a key for vocab B. The PRNG seed was the same. The cache was not. The eval was not stochastic. The eval was order-dependent in a way that was not in the seed.

It took me three weeks to find. The fix was thirty seconds. The lesson was not the fix. The lesson was that "reproducible" is a property of the system, not a property of the seed.

// 02   WHAT STATE IS

An agent evaluation environment is, formally, a stateful process. It receives an action from the agent, updates its internal state, returns an observation. An episode is a trajectory of state-action-observation tuples. A reset is a transition back to a known initial state. The reproducibility property we want is: given the same seed, the same episode produces the same trajectory.

What breaks reproducibility is the gap between "the state the env thinks it is in" and "the state the env actually is in." The env has a mental model. The env has a filesystem, a process table, a network namespace, a clock, a set of cached connections, a set of module-level globals. The reset is a function on the mental model. It does not necessarily touch the second list. When the two diverge, the env lies to itself, and the lie shows up in the data.

The naive way to think about state is the variable scope. A function-local variable goes out of scope at return. A class-level variable persists for the lifetime of the object. A module-level variable persists for the lifetime of the interpreter. A file on disk persists until something deletes it. A socket persists until it is closed. A child process persists until it exits. A clock keeps ticking.

The less naive way to think about state is the lifetime hierarchy. Reset, in most agent eval harnesses, is supposed to clear the env's logical state (the game world, the observable). It is not supposed to clear the env's physical state (the Python interpreter, the OS, the container, the network). The physical state is supposed to be initialized once and never change. The guarantee fails when the initialization of the physical state is order-dependent, random, or time-dependent.

DeepMind's Crafter benchmark (Hafner, 2021) makes this hierarchy explicit. The benchmark serves episodes from a deterministic world generator; the reset clears the world; the world is regenerated from the seed on the next episode. The physical state (the Python interpreter, the rendering context) is shared across episodes. The convention is that the world generator is pure. It is. Most eval envs are less careful.

// 03   THE FOUR FAMILIES OF LEAKAGE

The leaks I have seen cluster into four families. None of them are exotic. They are all things that "should not matter" in a hermetic environment.

Caches

Caches are the most common and the most subtle. A file system cache. An embedding cache. An HTTP cache. An in-process memoization table keyed on something other than the seed. The first run computes a thing. Every subsequent run reads the thing from disk and pretends to compute it. The result is correct. The first run is not.

The HuggingFace transformers tokenizer cache is a particularly clean example. The first time AutoTokenizer.from_pretrained() is called, it downloads the tokenizer files, builds the vocabulary mapping, and caches the mapping object in ~/.cache/huggingface/. Subsequent calls in the same process reuse the mapping. The first call after the cache is warm runs in microseconds. The first call on a cold cache runs in seconds. The eval timing reflects both. The eval result is the same. The eval timing is not, and timing affects everything downstream that uses timeouts, retries, or early stopping.

The functools.lru_cache decorator, in Python, is another frequent offender. The cache is keyed on the function arguments. The arguments look deterministic. They contain a list, or a dict, or an array, or an opaque token, in a way that the cache treats as equal when it isn't. The first call computes. The second call retrieves. The retrieved result is the right answer for the first call's input, not the second call's. The eval silently uses the wrong answer.

The cure is to make caches first-class. Give them a name, a TTL, and an explicit invalidation step in reset(). Caches that are invisible to the env's reset are caches that leak.

Global State

A module-level variable that holds a counter, a connection pool, a model handle, a logger, a thread-local storage. The reset clears the visible world. The variable is not part of the visible world. The variable is part of the interpreter. The interpreter persists across resets.

The classic case is the requests.Session object created at module import. The session has a connection pool. The connection pool has keep-alive sockets. The sockets have cookies. The cookies are the previous episode's cookies. The next episode authenticates with the wrong credentials. The eval silently uses a session that has the wrong identity. Reset does not touch the session. Reset was never supposed to.

The Mechatron env (LOG 001) has a related bug. The env keeps a module-level tokenizer object. The tokenizer object is shared across episodes. The vocabulary is the same. The internal state of the tokenizer (the merge table, the BPE-dropout counter, the byte-pair cache) is not. Two episodes that start with the same seed can produce different token sequences if one of them runs after the other has trained the BPE-dropout counter. The eval is a small amount wrong, in a way that compounds. We caught it by accident when we ran the same seed twice in a row and got different results.

The cure is to forbid module-level mutable state in environment code. Lint it. Refuse to merge it. The rule is the rule. The first exception is a regression in three weeks. The second is a refactor.

Filesystem Residue

Tool-using agents write to /tmp, to ./outputs, to a sandboxed path that wasn't actually sandboxed. The next episode inherits the previous episode's mess. Files overwrite each other. Lockfiles linger. The agent's working directory has artifacts from a previous task.

The dangerous case is the path that the env "resets" but doesn't actually. A common pattern: 

def reset(self):
    for f in os.listdir(self.workdir):
        os.remove(os.path.join(self.workdir, f))
    # ... reset logic ...

This works on the workdir. It does nothing about ~/.cache, /tmp/agent_*, or any other path the agent touched. The agent's tool registry does not have a list of paths it might have touched. The filesystem does. The filesystem is not reset.

The cure is a per-episode filesystem namespace. A tmpfs mount per episode, or a per-episode chroot, or a per-episode user namespace with isolated $HOME. We pay for the mount once and never think about it.

Time and Randomness

Seeds that are "almost" deterministic. A PRNG seeded with the episode id, but a datetime.now() call inside the tool registry that isn't. A hash function that uses Python's hash() for tuples (which is salted by PYTHONHASHSEED at interpreter start). A timeout that uses wall-clock time and so is affected by the host's load.

Python's PYTHONHASHSEED is the most over-looked source of nondeterminism in Python eval envs. String and tuple hashes are randomized at interpreter start. If the env stores anything in a set or a dict keyed on a string, iteration order is hash-dependent. Iteration order is part of the eval. The hash seed is process-local. Two processes have different hash seeds. The eval is not reproducible across processes.

JAX and Flax's explicit key model is the response. The user threads a PRNGKey through every function that uses randomness. The key is the only source of randomness. The function is pure. The output is reproducible. The cost is the user threading the key through everything. The benefit is reproducibility that does not depend on a process-wide seed.

// 04   DETECTION: SNAPSHOT DIFFING

The most useful detection technique I have found is the boring one. Run the environment in two modes: hermetic (a known seed, no agent input) and adversarial (a long sequence of agent actions). After each episode, snapshot the world. Every file under the workspace. Every environment variable. Every open socket. Every running process that the env could see. Diff the snapshots. Any state that survives a reset is a leak.

The skeleton is small: 

def assert_isolated(env, before, after):
    leaked = []
    for path in snapshot_paths(after):
        if not path.startswith(env.workspace):
            leaked.append(("outside_workspace", path))
        elif path in before and hash(before[path]) != hash(after[path]):
            leaked.append(("uncleared_workspace", path))

    for var in env.list_env_vars():
        if var not in before["env"] or before["env"][var] != env.get_env(var):
            leaked.append(("env_var_changed", var))

    assert not leaked, f"state leaked across reset: {leaked}"

The real implementation is messier. The filesystem snapshot needs to follow symlinks. The env-var snapshot needs to filter out variables that legitimately change between episodes (timestamps, temp paths). The process snapshot needs to handle PIDs that are re-used. The diff needs to be stable across runs. None of that is hard. All of it is tedious. The tedium is the point. The diff catches what dashboards cannot.

Running this once a week on every environment we ship has caught more reproducibility bugs than every other technique combined. It is also loud in a way that humans respect. A printout of "the file /tmp/agent_cache.json changed between episode 1 and episode 2" is easy to act on. A 2% regression on a dashboard is not.

The technique is not new. The Linux kernel has had proc/<pid>/root for filesystem snapshots since 2.6. Docker uses union filesystems with copy-on-write. The strace tool records every syscall. The auditd daemon records every filesystem event. The novelty, in agent eval, is using these tools as a unit test, not a debugging tool. The isolation test is a test that the env can be reset. It runs in CI. It fails when the env leaks. It cannot lie.

A passing test is not a guarantee of isolation. A test that fails the moment two episodes share a workspace is.

// 05   A CONCRETE CASE: THE MECHATRON TOKENIZER

The Mechatron env, the same one I described in LOG 001, has a textbook case of all four families in one bug.

The env uses GPT-2's BPE tokenizer to encode prompts to the agent. The tokenizer is a module-level singleton. It is created at interpreter start, cached on transformers.AutoTokenizer.from_pretrained's internal cache, and reused for every episode. The vocab is fixed. The internal BPE-dropout counter is not.

In the first version of the env, the tokenizer was being called with a dropout rate of 0.1, on the assumption that BPE-dropout was a form of regularization. It isn't regularization. It is a stochastic encoder. The probability of any given merge is 1 - dropout. The output token sequence for a fixed input is a random variable.

The first time I ran the eval, I got one number. The second time, I got a different number. The third time, I got a third number. The PRNG seed was the same. The output was not. The output was a function of the PRNG seed AND the BPE-dropout counter AND the order in which the merges had been computed. The PRNG was reset at the start of every episode. The BPE-dropout counter was not reset. The first episode used a counter value of 0. The second episode used a counter value of 47. The third used 113. The eval was using a stochastic encoder in a way that was not in the seed.

The fix was to set BPE-dropout to 0. The env, in the new version, deterministically encodes inputs. The PRNG seed is the only source of randomness. The eval is reproducible.

The cost, before the fix, was three weeks of debugging during which I assumed the model was the variable. The model was not the variable. The tokenizer was. The dashboard said the model was regressing. The dashboard was wrong. The dashboard was a function of the tokenizer counter, which was a function of the eval history, which was a function of nothing in particular.

The lesson is the only lesson state leakage ever teaches. The bug is always in the part of the system that was not supposed to be variable.

// 06   PRNG, TIME, AND THE LIMITS OF SEEDING

The most common response to a reproducibility bug is to "add a seed." The seed gets added. The bug persists. The seed is not the problem. The seed is one source of randomness. There are others.

The five sources of nondeterminism in a typical agent eval: 

SOURCE              COMMON VICTIMS               FIX
PRNG seed           numpy, torch, jax keys      pass seed explicitly
Wall clock          timeouts, retry budgets     use episode-relative time
Hash seed           set/dict iteration          PYTHONHASHSEED=0 or use JAX
Threading           race conditions, ordering   pin to single thread
External I/O        network, file timestamps    snapshot inputs, freeze I/O

Each of these has a known mitigation. The mitigations are well-understood. The mitigations are also not automatic. NumPy's random.seed() does not affect PyTorch's torch.manual_seed(). JAX's PRNGKey does not affect Python's random. The mitigations do not compose. The user has to thread the seed through every layer.

The Linux kernel's randomness is the deepest source. /dev/urandom reads from a pool seeded by interrupt timing and other entropy sources. Two processes see different entropy. The entropy leaks into Python's os.urandom(), into NumPy's default_rng(), into anything that initializes a PRNG without an explicit seed. The initialization is a one-time event. The output is deterministic after initialization. The output before initialization is not.

The fix is to make the initialization explicit. JAX's PRNGKey(seed) is the cleanest version. The function is pure. The output is a function of the input. The user threads the key through everything. The "default" randomness is never used. The kernel entropy never enters the system.

The deeper fix is hermeticity. Run the env in a container. Set the container's time to a fixed value. Bind /dev/urandom to a fixed seed. Mount the filesystem read-only. Disable the network. The env is then a function of the seed, the agent's actions, and nothing else. The function is reproducible. The function is also slow. Hermeticity is not free.

// 07   THE COST OF DRIFT

The cost of state leakage is not the leakage itself. The cost is the time spent chasing the wrong bug. The model did not regress. The prompt did not regress. The dataset did not regress. The drift was the env. The team spent two weeks assuming the model was the variable. The team could have been training a new checkpoint.

The cost compounds. A 1% drift, in a single eval, is below the noise floor of most model comparisons. A 1% drift, in a rolling baseline, looks like a slow improvement or a slow regression. A 1% drift, in a long-running training run, is a "training is not converging" diagnosis. A 1% drift, in a paper, is a result that does not replicate.

The case I think about is the SWE-bench reproduction cycle. SWE-bench (Jimenez et al., 2024) is the standard agent eval for software engineering. It was used to compare dozens of models in 2024 and 2025. Some of the comparisons were clean. Some of them were not. The non-clean ones were not clean because the Docker images used to evaluate the models had filesystem residue from previous runs, and the residue was in /root/.cache for the wrong Python version. The eval reported the right number for the wrong reason.

The cost, in that case, was months of "why does model X look better in our setup than the paper says." The answer was the setup. The setup was leaking. The paper was right. The setup was misleading the team. The team's conclusions were suspect for as long as it took to find the leak.

The honest version of an agent eval is one where the env can be re-run from scratch, with the same seed, and produce the same result, in a different container, on a different day, by a different person. If the eval cannot do that, the eval is not measuring what it says it is measuring. The eval is measuring itself.

// 08   POST-MORTEM

A few things I want to flag from my own work, separate from the broader argument.

The first is that snapshot diffing should be a unit test, not a debugging tool. The cost of running snapshot diffs in CI is small. The cost of running snapshot diffs only when a regression is suspected is large. We run snapshot diffs on every PR that touches an env file. We have caught leaks that were three lines long, in code that had been in production for months. The leaks were silent. The snapshot diff was not.

The second is that the four families are not exhaustive. They are the ones I have hit. The general pattern is the same: state that the env did not know it had, surviving a reset it was not supposed to touch. The pattern shows up in places I have not thought of. GPU memory, recently. The CUDA context is per-process, but the PyTorch caching allocator is per-thread, and the allocator's bookkeeping survives a reset in a way the env did not anticipate. Two episodes that allocate the same tensors in the same order get different memory profiles. The eval timing reflects the memory pressure. The eval results reflect the timing.

The third is that hermeticity is not a feature. It is the absence of a class of bugs that are very expensive to find and very cheap to prevent. The reward for getting it right is that your numbers stop drifting, your debugging sessions get shorter, and the model regressions you actually care about become visible again.

The full snapshot-diffing harness we use is in the same repository as the env code. The hermeticity tests, the per-episode tmpfs mount, and the PRNG threading rules are documented in the env README. The Mechatron env's full isolation suite is at huggingface.co/spaces/nebiuz/mechatron-env.
