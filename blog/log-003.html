Designing Agents That Can Undo Mistakes

The cleanest way to make a tool-using agent more reliable is to give it a real undo button. Not as a prompt instruction. As a system call. This post is about why prompt-level undo fails, what versioned environments look like, the three tools every agent should have, and where the pattern breaks down.

// 01   THE STUCK AGENT

The first time I traced a stuck agent, I expected to find a planning failure. The plan was fine. The plan was deterministic, well-structured, and produced by a model that could clearly enumerate the steps. The problem was at step 3. The agent had called the wrong tool. The wrong tool returned a result. The result was wrong. The agent's plan said "use the result of step 3 in step 4." The agent used the wrong result in step 4. Step 4's output was wrong. The agent's plan said "validate the output of step 4 in step 5." The agent validated the wrong output. The validation said "this looks good." The agent's plan said "if validation passes, proceed to step 6." The agent proceeded to step 6.

By step 9, the agent had built twenty lines of reasoning on top of a wrong premise. By step 14, the agent's commentary contained phrases like "given the result we computed earlier" and "as we established at the start of this task." The earlier result was wrong. The earlier result was the wrong tool's output. The agent knew, in some statistical sense, that step 3 had been a mistake. It had access to the full trajectory. It could see the wrong result. It could see the subsequent reasoning. It chose not to confront the mistake, because confronting the mistake meant admitting that steps 4 through 14 were reasoning on top of a bad premise, and admitting that is expensive in the autoregressive sense. The model prefers to keep going.

We had given the agent, in its system prompt, the line: "If you make a mistake, stop and reconsider your plan." The agent never used the line. The line is good advice for a human. The line is a hope for a language model. A language model continues the most likely sequence of tokens. "Stop and reconsider" is not a sequence of tokens. It is an instruction to break the pattern the model is in, and the pattern is strong.

// 02   WHY PROMPT-LEVEL UNDO FAILS

The intuition behind "if you make a mistake, stop and reconsider" is sound. The execution is not. A language model is a conditional probability distribution over the next token. The probability of "I made a mistake, let me rewind" is highest when the model has just produced a token sequence that admits a mistake. The token sequence that admits a mistake is the token sequence that is locally consistent with a mistake having been made. The mistake, if it occurred at step 3, is now buried under eleven steps of reasoning. The local context at step 14 is "I have just validated step 13." The probability of the next token being "actually, step 3 was wrong" is dominated by the probability of the next token being "and step 14 should produce..." The model is, in a real sense, walking forward.

The Reflexion paper (Shinn et al., 2023) tried to fix this by adding an explicit self-reflection step. The agent generates a verbal reflection on the trajectory so far, then re-prompts itself with the reflection in context. Reflexion works in toy environments. It works less well in long-horizon agent tasks, where the reflection itself becomes part of the context the model is reasoning about, and the model can be talked out of its own reflection as easily as it can be talked into one. Self-reflection is a soft intervention. It does not change the environment the model is operating in. It changes the model's narration of the environment. The narration drifts.

Self-Refine (Madaan et al., 2023) tries iterative refinement. The model generates an output, critiques it, and regenerates. The critique is a learned behavior, and it suffers from the same training-distribution problem that LLM judges suffer from (see LOG 001). The model is critiquing itself with a model that shares its training data. The critique drifts toward "this looks plausible" rather than "this is correct."

The deeper issue is that all of these interventions operate on the model's narration of the world. They do not operate on the world itself. A wrong tool call, once made, is made. The world has changed. The model's narration of the world is the only thing the prompt can touch. The world and the narration diverge, and the divergence is what the agent gets stuck on.

The fix is to make the world itself undoable. Not as a metaphor. As a system call.

// 03   TRANSACTIONS IN THE DATABASE WORLD

The pattern we want is not new. Databases have had transactions for fifty years. The ACID properties (atomicity, consistency, isolation, durability) were formalized in the 1980s. The intuition is simple: a transaction is a unit of work that either happens or doesn't. The world is either in state S1 or state S2. There is no state in between. The agent does not need to clean up the in-between; the in-between does not exist.

Modern databases go further. Multi-Version Concurrency Control (MVCC), introduced in the 1970s and refined in PostgreSQL and InnoDB, gives every transaction its own snapshot of the database. A read at time T1 sees the world as of T1. A write at T2 produces a new version. A reader at T3 can be pointed at T1, T2, or T3, depending on which snapshot they want. The world is a log of versions. Any version is reachable. The past is not deleted; it is shadowed.

The FoundationDB record layer pushes this further with conflict-free transactions across a distributed store. Calvin (Thomson et al., 2012) and Spanner (Corbett et al., 2012) showed that global transactions could be ordered by a consensus protocol and committed with strict serializability. The price is latency. The benefit is that any read is a snapshot of a consistent past, and any write is either applied or not.

The pattern we want for agents is the same pattern, in a smaller and more local form. Every state-mutating tool call is a transaction. The agent sees the world as a sequence of versions. The agent can commit a version as a checkpoint. The agent can roll back to a checkpoint. The agent can list the checkpoints and the operations between them. The pattern is not novel. The novelty is applying it to an agent's interaction with its environment, where the "database" is a workspace and the "transactions" are tool calls.

// 04   VERSIONED ENVIRONMENTS

The versioned environment is a thin layer between the agent and the underlying store. The store can be a filesystem, a database, a Kubernetes cluster, or a remote API. The layer intercepts state-mutating operations, records them as versions, and exposes a small API for navigating the version history.

The simplest implementation is content-addressed: every state version is a hash of its contents. The hash is the version id. A commit takes the current state, computes its hash, stores the hash in a log, and returns the commit id. A rollback takes a commit id, fetches the corresponding state, and replaces the current state. The log of commits is the history.

The git object model is the canonical example. A commit is a tree of blobs, identified by their hashes. A branch is a pointer to a commit. A reset moves the pointer. The history is a directed acyclic graph of commits. The model is small, the implementation is well-understood, and the pattern maps cleanly onto agent state.

We have used three implementations in production. The first was a simple file-tree snapshotter: every commit recursively hashed the workspace, stored the hash, and the rollback restored from the hash. The second was a copy-on-write overlay filesystem at the kernel level, similar to Docker's storage driver. The third is the one we use now: a CRDT-backed state store with per-episode branching, where each commit is a logical operation and the rollback is a replay of the operations up to the target commit.

The CRDT version is the most expensive in absolute terms and the cheapest in cognitive terms. The agent sees a "current state." The current state is a function of the operations applied. The agent's view is always the latest version. The agent can rewind by reverting operations. Conflicts between concurrent operations are resolved by the CRDT, not by the agent. The agent never sees a half-applied state.

// 05   THE THREE TOOLS

The agent's interface to the versioned environment is three tools, no more. The model does not need to know about transactions, MVCC, or content-addressed storage. It just needs to know that commit is cheap, rollback is cheap, and history is observable. 

env.commit()          # mark current state as a checkpoint
env.rollback(to=n)    # rewind to checkpoint n, drop everything after
env.history()         # list of commits and their hashes

The naming matters. We tried "save," "restore," and "list-saves" in an early version. The model did not use them. We tried "checkpoint," "rewind," and "log." Slightly better. We landed on "commit," "rollback," and "history" because those are the words the model has seen in the largest number of contexts (git, databases, transactional systems). The vocabulary matches the model's prior. The model uses the tools more often when the tool names match its prior.

The behavior change is dramatic. Agents start using commit aggressively, usually every one or two steps, because the cost is zero and the upside is obvious. We did not have to tell them to. They figured it out within a handful of episodes. The pattern is not specific to any one model. We have observed it in Claude, GPT-4, Qwen, DeepSeek, and others. The behavior is a function of the tools, not the model.

The cost of a commit, in our CRDT-backed implementation, is approximately 1.2 milliseconds on a workspace of 10,000 operations. The cost of a rollback is similar. The cost of a history call is proportional to the number of commits, but we cap the visible history at the last 50 commits, with explicit "show older" calls available. The cheap path is actually cheap. The agent uses it.

// 06   WHAT CHANGES

Once rollback is a primitive, three things happen, all of them good. The first is that trajectories shorten. Agents stop compensating for early mistakes and start fixing them. Total steps per task drops noticeably on long workflows. We saw a 30% drop on the DataJanitor cleaning tasks after we shipped the versioned env. The distribution of trajectory lengths also tightens. The long tail of "stuck agent" trajectories disappears. The variance between runs of the same task drops.

The second thing that changes is that reasoning gets sharper. When "I was wrong about step 4" is a tractable problem, the model is willing to confront it. The apologetic, hedging style of stuck agents disappears. The model rolls back, makes a different choice, and proceeds. The "actually, let me reconsider" prompt-instruction is no longer needed. The model is not reconsidering. It is undoing. The undo is a system call. The system call is faster than the reconsideration. The agent's narration follows the system's lead.

The third thing is that debugging gets easier. Every rollback leaves a trail. You can ask "what did the agent do between commit 3 and commit 7" and get a precise answer, instead of reading a fifty-step log and guessing. The trail is structured. The trail is queryable. You can filter by tool, by time, by error type. You can replay a specific window of the trajectory with a different model. The debugging tools you would have built for the agent are now the agent's own logs, structured by the same primitive the agent uses.

The cost, of course, is infrastructure. A versioned env is more code than an unversioned one. The versioned env needs to handle edge cases (concurrent commits, partial failures, replay of side-effecting tools). The versioned env needs to be tested (does a rollback actually restore the state? does a commit capture everything? does the history match the actual sequence of operations?). The cost is real. The benefit is that the rest of the agent becomes simpler, because the safety net is in the right place.

Tools that make the safe path the easy path are tools that get used. The model will not carefully read a paragraph of prompt-level instructions. It will absolutely call a one-token tool that has no downside.

// 07   THE DRY-RUN BOUNDARY

Not every action should be rollback-able. An email sent to a real person cannot be unsent. A payment submitted to a payment processor cannot be unsubmitted. A file written to a remote storage system may be cached in places the agent cannot reach. The rollback primitive stops at the environment boundary. The environment boundary is the set of operations whose effects the env can reverse.

For operations outside the boundary, the answer is a dry-run mode. The env exposes a preview tool that runs the operation without committing it. The agent gets the would-be result, can inspect it, and can then choose to commit. The dry-run is a different operation than the real one. The real one has side effects. The dry-run does not. The agent learns the distinction by experience, and the distinction is part of the tool's description.

The dry-run pattern is borrowed from databases' BEGIN / COMMIT / ROLLBACK semantics, and from the CQRS pattern in event-sourced systems. The command side proposes a change. The query side reports what would happen. The commit is a separate event. The dry-run is the query side. The commit is the command side. The rollback is the absence of a commit.

In our agents, the dry-run is used heavily before any tool that touches the outside world. The agent runs the dry-run, reads the preview, and only commits when the preview matches its intent. The commit rate for side-effecting tools is around 60% (the agent previews, decides the preview is wrong, and tries again). The commit rate for local-only tools is close to 100%. The pattern is the same. The cost of a wrong commit is different. The tool design reflects the cost.

// 08   POST-MORTEM

A few things I want to flag from our own work. The first is that the versioned env is not a silver bullet. Some failure modes are not solved by rollback. A model that commits to a wrong plan and never encounters a tool error will not roll back. A model that has a wrong goal will not roll back. Rollback fixes the class of bugs where the model makes a recoverable mistake. It does not fix the class of bugs where the model has a wrong plan or a wrong goal. Those require different interventions (better planning, better prompting, or, in extreme cases, a different model).

The second is that the versioned env is not free at scale. A long-running agent, over thousands of tool calls, accumulates a history that grows without bound. The history must be checkpointed, compacted, or both. We have a soft cap of 50 visible commits in the agent's view, with explicit "show older" calls for the rest. The older commits are still on disk. They are just not surfaced by default. The cap is a UX choice, not a correctness one.

The third is that the dry-run pattern is harder than it looks. The dry-run must produce the same response shape as the real tool, must not have side effects, and must be observably different (so the agent and the human reviewer can tell which mode was used). The tooling required to make a tool "dry-run-able" is non-trivial. We have a small library of base classes that handle the common case (HTTP calls, database writes, file operations). New tools that are not derived from the base classes have to implement the dry-run contract manually. About 20% of our tools do this. The other 80% inherit it. The pattern is opt-out, not opt-in.

The versioned env, the dry-run pattern, and the three tool APIs (commit, rollback, history) are all in the open-source release of our agent runtime, which we published in March 2026. The full source, the test suite that exercises the rollback semantics, and the benchmark we use to measure the trajectory-length reduction are at huggingface.co/spaces/nebiuz/agent-runtime. The versioned env builds directly on the MVCC semantics of FoundationDB, the content-addressed storage of git, and the CQRS pattern of event-sourced systems. The novelty, to the extent there is one, is putting those three patterns together and exposing them as tools to a language model.
