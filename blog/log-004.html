A Small Event Bus Is All Your Agent Needs

Replacing the imperative control flow inside an agent with a typed event log is a refactor I would do earlier and more often. It costs you almost nothing and unlocks three things you wanted anyway: replay, observability, and parallelism. The model is not special. It is one more handler in a pipeline that runs on a log.

// 01   THE CHAIN BREAKS

The first version of any agent is a chain. plan → act → observe → decide → act → observe → ... It is the shape every tutorial teaches, and it is the shape that breaks first. The chain works for one task with three tools. It does not work for a workflow with ten tools, two retrievers, a human in the loop, and a webhook listener. The control flow becomes an unreadable ladder of conditionals, and every new feature is a new branch in a tree nobody wants to draw.

I watched this happen on a real codebase in early 2025. A 400-line agent went to 1,200 lines in three months. The model changed twice. The tool registry grew from 5 to 14 tools. A human-in-the-loop step was added at the midpoint. The conditional depth went from 2 to 5. The runtime correctness went from "passes most of the time" to "passes occasionally." The team spent more time debugging the control flow than improving the prompts. The prompts were fine. The prompts were being executed by code that had grown past the point where anyone could reason about it.

The ReAct paper (Yao et al., 2022) formalized the chain as reasoning + acting: at each step, the model produces a thought, an action, and an observation. The pattern is elegant in the paper. In production, the pattern produces three types of code: the chain itself, the wrapper around the chain, and the wrapper around the wrapper. The chain is fine. The wrappers are where the bugs live.

The deeper issue is that the chain is a state machine, but the state is implicit. The state lives in the closure of the function that runs the chain. The state is not serializable, not queryable, not replayable. When the agent fails at step 14, you cannot ask "what was the state at step 7" without re-running the whole chain. When the agent succeeds, you cannot ask "what would have happened if the model had picked a different tool at step 4" without re-running with a different model. The chain is a single thread of execution. The chain is the only execution you have. The chain is the only execution you can have.

// 02   FROM CHAIN TO LOG: EVENT SOURCING

The fix is to stop calling tools and start emitting events. The pattern has a name. Martin Fowler called it event sourcing in 2005. The idea is simple: rather than storing the current state of the system, store the sequence of events that produced the current state. The current state is a function of the events. The events are the source of truth. The state is derived.

The pattern is not new. Domain-driven design has had domain events since the mid-2000s. CQRS (Command Query Responsibility Segregation) extends the pattern by separating the write side (commands that produce events) from the read side (queries that derive state from events). Apache Kafka made the pattern operational at internet scale in the early 2010s. EventStoreDB and similar systems packaged the pattern as a database.

For agents, the pattern is almost too natural. An agent is a system that produces and consumes events. The events are the actions the agent takes, the observations the agent receives, the decisions the agent makes. The events are already what the agent is doing. The only change is to make the events first-class.

The event log, in our agents, is a list of typed records. Each record has a stable name, a timestamp, a payload, and a unique id. The types are Pydantic models in Python or dataclasses in Go or Rust. The naming is dotted, in the CloudEvents style: plan.requested, tool.called, tool.returned, plan.completed. The names are stable. The payload shape is stable. The id is a UUID. The timestamp is monotonic per agent run. 

@bus.handler("plan.requested")
def on_plan(req: PlanRequested) -> list[Event]:
    steps = planner(req.goal)
    return [PlanProduced(plan=steps) for s in steps]

@bus.handler("tool.called")
def on_tool(call: ToolCalled) -> list[Event]:
    result = registry[call.name].run(**call.args)
    return [ToolReturned(call_id=call.id, result=result)]

Tools become handlers. The handler takes an event, does some work, and returns zero or more events. The runtime is a loop. It pulls the next event from the log, dispatches it to the matching handlers, appends the results, repeats. The agent's "decision" is just another event. The model is a handler that takes the current log slice and produces the next action event. The control flow moves out of your code and into the log.

// 03   THE RUNTIME

The runtime is the smallest part of the system. It is a loop, a dispatch table, and a log. The loop pulls the next unhandled event. The dispatch table maps event types to handler functions. The handler runs. The returned events are appended to the log. The loop continues until the log contains a terminal event (run.completed or run.failed), until a timeout, or until a max-iterations cap.

The runtime does not know about tools. The runtime does not know about the model. The runtime does not know about the agent. The runtime knows about events, handlers, and a log. The model is a handler. A tool is a handler. A retriever is a handler. A human-in-the-loop step is a handler that waits for an external event. The only special handler is the one that produces the next action, which is the one that calls the LLM.

The advantage of this separation is that the LLM call becomes a regular handler. It can be replaced, retried, cached, or mocked without changing anything else. The rest of the system does not care whether the action was produced by a model, a cached lookup, a heuristic, or a human. The rest of the system only cares that an event of the right type was appended to the log.

The implementation we use is small. About 200 lines of Python for the core. The dispatch table is a dict from event type to handler. The handler signature is (event) -> list[Event]. The log is an in-memory list during a run, flushed to disk or object storage at the end. The events are JSON-encoded. The runtime is single-threaded by default. Parallelism is a runtime concern, not a handler concern (see section 7).

// 04   THE EVENT LOG AS A DATABASE

Once the log is the source of truth, the log is a database. Not metaphorically. The log is a write-once, append-only, ordered sequence of records. That is a database. The records are queryable. The records are joinable. The records can be aggregated, filtered, and windowed with the same primitives a traditional database supports, plus the time-ordering semantics that traditional databases do not have natively.

The query primitives that become natural:

  • Filter by type. "Show me every tool.called event in the last 30 days." The index is the event type. The query is a scan of the index. The latency is bounded by the index size, not the log size.
  • Window by run. "Show me the events of run R." The run id is a tag on every event. The query is a filter on the run id. The result is the trajectory.
  • Join on parent. "Show me every tool.returned that followed a tool.called within 5 seconds." The join key is the call id. The result is the tool latency distribution.
  • Aggregate by handler. "How many events did the model handler produce per run, on average, by task class?" The aggregation is a group-by on a derived column.

The log is also a stream. The same events that go into the log can be published to a broker (Kafka, NATS, RabbitMQ) for downstream consumers. Dashboards, alert systems, and other agents can subscribe to the stream without coupling to the producing agent. The producer and the consumers share only the event schema. The producer does not know who the consumers are.

The implementation we use for the query layer is ClickHouse. Events are flushed from the in-memory log to a ClickHouse table with a schema derived from the event types. The schema is versioned with the event types. Migrations are handled by ClickHouse's ALTER TABLE ... MODIFY COLUMN primitives. Most queries on a week of event data return in under 100ms. The latency is dominated by the network hop, not the query.

// 05   REPLAY

The first thing you notice when the agent's state is a log is that replay is free. The log is the trace. Given the same starting state and the same events, the run is reproducible, including the model's choices, because the model's inputs are just a slice of the log. The model is a handler. The handler is a pure function of its inputs. The inputs are in the log. The run is reproducible.

Reproducibility is the foundation of three things that are otherwise hard. The first is debugging. You can stop a run, inspect the log, and identify the event that caused the wrong outcome. You can then mutate that event, replay from there, and observe the different downstream behavior. The replay is the debugger. The mutated event is the breakpoint.

The second is evaluation. You can take a production log, run it through a different model, and compare the new outcomes to the recorded ones. The comparison answers "would model B have done better on this trajectory?" The log is the test case. The new model is the implementation under test. The eval is the comparison. No new infrastructure required.

The third is regression testing. You can take a snapshot of a passing log, replay it on every PR that touches the agent code, and assert that the run still passes. The snapshot is the regression test. The replay is the assertion. The CI is the runner. The pattern is borrowed from record-replay debuggers like Mozilla's rr and the Time Travel Debugging in Visual Studio. The novelty is applying it to a model-driven system.

The catch is that not every event is replayable. A send_email event that actually sent an email should not be replayed. We tag those events with a side_effect flag. The replay engine skips them by default. The flag is the difference between a debugger and a liability.

// 06   OBSERVABILITY

The second thing you notice is observability. A log of typed events is a structured query. "How many runs hit the rate limiter on the third tool call" is a single line of SQL instead of a regex against a string buffer. "Which step the agent is stuck on" is a histogram. You can build dashboards on top of the log without writing a parser. The dashboards are free. The dashboards are correct. The dashboards update as the event types evolve.

If your agent's state is a chain, debugging it is archaeology. If your agent's state is a log, debugging it is a database query.

The metrics that fall out for free:

  • Handler invocation counts. How many times did the model handler run per task class? Per run? Per minute? The answer is a COUNT on the event log.
  • Handler latency. What is the p50 / p95 / p99 latency of each handler? The answer is a percentile aggregate on a timestamp diff.
  • Tool retry rates. How often does a tool.called event get retried? The answer is a join on the call id.
  • Stuck-run detection. Which runs have not appended a new event in 60 seconds? The answer is a query on the latest event timestamp per run.
  • Cost attribution. How many tokens did the model handler consume per task class? The answer is a sum on a payload field.

None of these require instrumentation beyond the event log itself. The event log is the instrumentation. The event log is the observability. The dashboards are views onto the log. The alerts are queries that fire on conditions. The whole stack is one database and one query language.

// 07   PARALLELISM

The third thing, the one that surprised me, is parallelism. A chain is inherently sequential: step two depends on step one's result. A log of independent events is not. Once a handler emits two or more events with no ordering constraint, the runtime can dispatch them concurrently. In our retrieval-heavy agents, this collapsed end-to-end latency by a factor of three on a single-machine setup, with no changes to the model.

The runtime we use detects independence by inspecting the event payloads. Two events are independent if they do not read or write the same keys. The keys are declared in the event type's schema. The runtime maintains a small read/write set per in-flight event. When a new event is ready to dispatch, the runtime checks whether its declared reads are blocked by any in-flight event's writes. If not, dispatch. If yes, wait.

The pattern is structured concurrency, in the Trio sense. The agent's "concurrency tree" is implicit in the event log. The runtime materializes the tree from the log. The tree is observable: you can inspect the in-flight events and see which are blocked, which are running, and which are ready.

The caveats are real. Concurrency introduces races that the model can sometimes reason around and sometimes cannot. Two tools that update the same file are not safe to run concurrently, even if the model "intends" them to. The runtime enforces the read/write sets. The model can suggest. The runtime decides.

// 08   CAVEATS

Two things to be careful about. The first is that the event log grows. For long-running agents, you need either a checkpointing strategy or a windowed view that the model sees. We feed the model the last N events (typically 20) plus any events it explicitly asks for via a history(since=...) call. The full log is on disk. The model sees a slice. The slice is what the model reasons about. The full log is what the operator reasons about.

The second caveat is that the event log is a liability in the same way that any database is a liability. A log that contains prompts and responses is a log that contains PII, IP, and potentially regulated data. The log needs retention policies, access controls, and redaction. The events need to declare which fields are sensitive. The runtime needs to respect the declarations. The same hygiene that applies to a production database applies to the event log, with no exceptions.

The third caveat is that the event-sourced pattern requires the team to think in events. The chain is intuitive. The log is less so. New team members will reach for the chain first. The pattern is worth the ramp-up. The ramp-up is a one-time cost. The chain's complexity is a recurring cost.

// 09   POST-MORTEM

A few things I want to flag from our own work. The first is that the migration from chain to log is not always worth it. For a single-task agent with three tools and no human in the loop, the chain is fine. The log pays off when the system has more than one consumer of its state (a dashboard, an evaluator, a debugger, another agent). The break-even point in our experience is around 800 lines of agent code. Below that, the chain is simpler. Above that, the chain is a liability.

The second is that the runtime is the part you should over-engineer. The runtime is the part that touches every event. The runtime is the part that, if it has a bug, corrupts every run. The runtime needs to be tested with the same discipline as a database engine. The runtime needs to handle the edge cases (concurrent commits, partial failures, replay of side-effecting events). The runtime is the part that should have a formal specification. The handlers can be loose. The runtime cannot.

The third is that the CloudEvents-style naming is a small thing that matters a lot. Stable event names let you build dashboards, alerts, and migrations on top of the log without coordinating with the producers. The producers can rename their internal variables freely. The event names are the contract. The contract should be small, stable, and documented.

The runtime, the dispatch table, the replay engine, and the ClickHouse query layer are documented in the agent-runtime repo. The DataJanitor and Mechatron agents both run on the same event-bus runtime. The full source and the test suite are at huggingface.co/spaces/nebiuz/agent-runtime.
